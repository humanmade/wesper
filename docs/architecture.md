# How Wesper works

Wesper has two jobs: collect a WordPress site's capabilities into a JSON manifest, and help consumers read that manifest. It does not call AI models or change WordPress content. Start with the [README examples](../README.md#try-it-without-wordpress) to see the input and output.

## Live collection

```text
collect(options)                         src/index.ts
  ├─ WP-CLI                             src/collector/wpcli.ts
  │    execFile(wp, argv)
  │    --exec observer, before WordPress loads
  │    WordPress bootstrap → registration observations
  │    wp eval → PHP collection payload → JSON
  └─ core WordPress REST endpoints       src/collector/rest.ts
       optional authentication; anonymous results are partial
       request and validate each slice; retain useful partial results
                  ↓
normalizeCollectorOutput                src/collector/normalize.ts
  redact input → build and sort sections → derive coverage
  validate/default → final redaction and validation → sourceHash
                  ↓
enforceStrict, if requested              src/index.ts
                  ↓
SiteContext manifest
```

The WP-CLI observer records post-type and taxonomy registration call paths in memory before the main collection payload runs. It does not change registrations or install code on the site. Both collectors use shared normalisation; their evidence differs because core REST cannot expose everything WP-CLI can inspect. See [collector access and limitations](../README.md#collectors).

## Reading saved JSON

```text
untrusted JSON
  validate(input)                        src/index.ts
    redact → schema check/defaults → preserve evidence
  ValidationResult
    ok + context → lookup / compatibility / focus / summary helpers
    errors       → caller handles invalid input
```

This path needs no WordPress connection. Validate input before passing it to consumer helpers. `validate()` preserves evidence about omitted sections so that schema defaults do not turn missing information into confirmed absence. It does not recollect the site or verify the supplied source hash. See the [hashing and validation contract](../README.md#binding-join).

`focusContext()` returns a selected view, not a replacement full manifest. A consumer owns any design choices, authoring or changes made using Wesper's output.

## Example: tracing a collected field

The existing `contentModel.postTypes[].owner` field shows the route for an addition that only one collector can observe:

1. **Define the contract.** In `src/schema.ts`, `registrationOwnerSchema` distinguishes a matched owner from an unknown owner with a reason. The post-type record makes `owner` optional, allowing older manifests and collectors without this evidence. `src/types.ts` derives the public manifest type from the schema.
2. **Collect evidence at its source.** In `src/collector/wpcli.ts`, `PHP_REGISTRATION_OBSERVER` captures registration calls. The PHP function `wesper_registration_owner()` maps those observations to known packages; the post-type loop writes its result to `owner`. An ambiguous or unobserved caller stays unknown.
3. **Check the other collector.** `src/collector/rest.ts` maps core post-type endpoint records. Those endpoints provide no registration-caller evidence, so this collector omits `owner`. A plugin-name guess would change the meaning of the field.
4. **Preserve the value through normalisation.** `normalizeCollectorOutput()` passes post types through `sortPostTypes()`. That helper retains record properties while sorting fields and taxonomy names; schema validation checks the ownership value. Redaction and hashing apply to the returned document.
5. **Check both presence and absence.** [`content-ownership.test.ts`](../src/collector/content-ownership.test.ts) covers older manifests, invalid ownership evidence and REST's omission of owners. [`wpcli.test.ts`](../src/collector/wpcli.test.ts) exercises the collector. For a collection behaviour change, follow the [WordPress verification guidance](../CONTRIBUTING.md#keep-verification-focused) as well.
6. **Generate the shipped schema.** Run `npm run generate:schema` after changing the schema source. Review the generated diff; do not hand-edit the JSON Schema as the source of truth.

For another field, use both collectors when both can observe the same fact. When one cannot, preserve the contract's missing/unknown representation and its coverage rules. Do not substitute an empty registry for evidence that was never read.

## Terms used by the API

| Term | Meaning |
|---|---|
| Manifest | The saved `site.context.json` description of the site. |
| Provenance | Collection metadata, including collector version, collection time and source hash. It is evidence about the snapshot, not proof of current runtime behaviour. |
| Coverage | Whether a surface was read completely, partly or was unavailable. A valid manifest can still be partial. |
| `found`, `absent`, `unknown` | Lookup results. `absent` requires complete evidence; `unknown` means the evidence cannot settle the lookup. |
| Native token reference | WordPress's own reference to a theme preset. For example, the colour preset `primary` can expose `var:preset|color|primary` as its block-style reference. The name does not establish its design role. |
| Owner | Package attribution with an evidence type. A block metadata match identifies a candidate; an observed registration caller identifies registration evidence. Neither proves rendering behaviour or the package's full footprint. |

See [native references and coverage](../README.md#native-references-and-coverage), [compatibility checks](../README.md#compatibility-checks) and [package attribution](../README.md#package-attribution-and-taxonomies) for the detailed contracts.

## Extension boundaries

`collect()` supports the built-in WP-CLI and REST collectors. There is no public custom-collector registration API. `fixture` labels synthetic manifest provenance; it is not a live collection option.

Consumers use the exported validation and helper functions without depending on collector internals. The schema accepts additive JSON properties for forward compatibility, but the live normaliser builds known sections; this does not provide arbitrary custom-collector passthrough.

Abilities collection, MCP and WordPress mutations are outside the current implementation. Setup and check commands live in [CONTRIBUTING.md](../CONTRIBUTING.md).
